## What the run showed

Two of the three failures are the source defect this slice is about, and both name `Q8_0`:

* `state_copy_ranges_tile_a_state_buffer_with_no_gap_or_overlap` — a 1-row q8_0 segment of a
  one-block row is 34 data bytes; differenced prefixes call it 36, because `kv_fmt_bytes`
  rounds a q8_0 buffer up to a `u32` multiple. The segments therefore do not tile: each one
  overlaps the next by up to 2 bytes, or leaves a 2-byte hole.
* `state_copy_seed_prefix_copies_exactly_the_seeded_rows` — a 5-row q8_0 prefix is 510 bytes,
  the sizer difference says 512. This is the live `SeamKv::seed_from` number, passed straight
  to `Backend::copy_buffer`, so the seeded window runs 2 bytes into the first row that was not
  seeded.

The third failure was a bug in the test itself, not in infr: `state_copy_subrange_selects_the_bytes_llama_v1_selects`
asserted that the block found at `off + len - block_bytes` is `first_block_of_row(r1 - 1)`. That
holds only at one block per row; at 3 blocks per row (`F16`, the first format in the roster) the
range's last block is the row's THIRD block, so the check compared 20 against 18 and aborted the
test. It is corrected to the last block of row `r1 - 1` — `(r1 * row_elems / block_elems) - 1` —
which also lets the format loop reach `Q8_0` and report the pad there instead of stopping at the
test's own arithmetic.

The three passing tests are the evidence that the pin's bug class is absent, not present:
`state_copy_q4_0_the_pin_selects_a_32x_shorter_range_than_v1` reproduces llama.cpp's
`3612199ed` arithmetic (2304 bytes of a q4_0 sub-range re-sized as 128 elements covers 72 bytes)
and `state_copy_f32_recurrent_state_ranges_are_the_whole_buffer` shows the f32 DeltaNet state the
MTP checkpoint copies is exact because `ggml_blck_size(f32) == 1`.
